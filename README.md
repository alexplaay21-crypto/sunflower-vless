# Sunflower Utility Proxy

Android-клиент для пользовательских VPN/proxy-подписок и конфигураций
(VLESS/VMess/Trojan/Shadowsocks) поверх Xray-core. Package:
`com.sunflower.utilityproxy`.

## Статус: v0.10 — светлая тема заработала по-настоящему, юнит-тесты, локализация

**Реальный баг, а не гипотетический:** `theme` хранился в DataStore и
отображался в `SettingsUiState`, но нигде не влиял на UI — ни пикера в
Settings, ни переключения в `SunflowerTheme` (жёстко всегда тёмная) не
было. Добавлена `SunflowerLightColors`, реальный пикер (Система/Светлая/
Тёмная), `MainActivity` подписывается на `SettingsRepository.theme` и
прокидывает в `SunflowerTheme`. `GlassCard` применён на оставшихся
экранах (Settings/Logs/Reset/About) — весь UI теперь единообразен.

**19 юнит-тестов** на все 4 парсера и `SubscriptionDecoder` (JUnit4 +
Robolectric — `android.util.Base64`/`org.json.JSONObject` не работают в
чистом JVM-тесте без него). Все base64-фикстуры вычислены и
провалидированы round-trip'ом через Python перед вставкой в тесты, не
набраны руками — один черновик поймал реальное расхождение (см.
`VmessUriParserTest.kt`, doc-комментарий).

**Локализация:** весь пользовательский текст экранов (61 строка) вынесен
в `values/strings.xml` (английский, дефолт) и `values-ru/strings.xml`
(русский) — оба набора ключей сверены построчно, идентичны. Каждая
`R.string.*` в коде сверена с реальным определением в XML скриптом — 0
расхождений. Сообщения об ошибках из data/parsing/tunnel слоя (например,
"Не удалось обновить подписку") НЕ локализованы — это отдельная
архитектурная задача (нужны коды ошибок вместо готовых строк, чтобы UI-
слой сам выбирал локализованный текст), не просто перенос литералов.

## Статус: v0.9 — release-сборка защищена (R8/ProGuard), Happ не анализировался

`isDebuggable = false` явно, keep-правила под WorkManager (резолвинг
Worker-класса по имени в рантайме) и задел под будущий JNI-keep для
libXray, `-assumenosideeffects` для Log.v/Log.d на будущее (в коде их и
так не было). Реальным grep по всему дереву исходников проверено:
хардкод паролей/токенов/секретов, тестовые/staging URL, случайно
закоммиченные keystore/credential-файлы — 0 совпадений. Честный список
того, что нельзя подтвердить без живой сборки (APK-размер, факт
обфускации, реальный запуск) — в `ARCHITECTURE.md`.

Анализ/декомпиляция `Happ.apk` через JADX/apktool не выполнялись — нет
сети для скачивания APK, и это противоречило бы собственному требованию
исходного промта не копировать proprietary-части HAPP.

## Статус: v0.7 — весь достижимый без AAR функционал

За этот проход: Автозапуск (флаг + BootCompletedReceiver), Логи (in-memory,
с редактированием чувствительных данных), Сброс (4 действия, каждое за
подтверждением), О приложении, Избранное на серверах, реальное
планирование WorkManager (интервал в Settings реально ставит/снимает
периодическую задачу), deep links для всех четырёх схем (subscription-URL
→ предзаполненный Add Subscription, серверная ссылка → прямой импорт как
Local), foreground-уведомление для VPN-сервиса (без него Android убивает
долгоживущие VPN-сервисы в фоне). Также честно задокументирована находка:
fragment/noises — поля отдельного `freedom`-outbound (подтверждено), но
переключатель в Settings сознательно не добавлен, пока не проверена
dialerProxy-связка outbound'ов.

С этой версии всё, что не зависит от появления `.aar` libXray, либо
сделано, либо явно и по конкретной причине отложено — таблица статуса
ниже это отражает по каждому пункту отдельно, а не общей фразой
"осталось доделать".

## Статус: v0.6 — outbound-схема всех 4 протоколов сверена по-настоящему

Проверил Trojan и VMess по их собственным официальным страницам
(xtls.github.io/en/config/outbounds/{trojan,vmess}.html), а заодно
пересверил VLESS — и обнаружил вторую ошибку: все три протокола
(vless/vmess/trojan) документированы с **плоским** `settings`
(`{address, port, id/password, ...}`), а не `vnext[]`/`users[]`/
`servers[]`, которые я использовал раньше по аналогии друг с другом.
Для VLESS обе формы валидны (упрощённая рерайтится во vnext внутри
парсера — подтверждено отдельно), но для Trojan/VMess массив вообще не
годился. Отдельно — актуальная VMess-документация не содержит `alterId`
как поле outbound-настроек вовсе. `XrayConfigBuilder` переписан на
единую плоскую форму для всех четырёх протоколов, с датами проверки
каждой страницы в комментарии файла.

## Статус: v0.5 — исправлена механика TUN, по первоисточнику

Проверил `proxy/tun/README.md` именно в самом Xray-core (не пересказ
через libXray) — предыдущее предположение про `env.xray.tun.fd` в JSON
было неточным. На самом деле: (1) конфиг обязан содержать
`inbound.protocol = "tun"` — это подтверждённый, реальный inbound; (2)
fd передаётся НЕ через JSON, а как настоящая переменная окружения
процесса `XRAY_TUN_FD`, через `android.system.Os.setenv` прямо перед
запуском. `XrayConfigBuilder`, `XrayTunnelEngine`, `TunnelManager` и
`SunflowerVpnService` переписаны под это. Готовый пример конфига и
разбор источников — в `ARCHITECTURE.md`.

## Статус: v0.4 — экран «Серверы» реально нажимаем

`XrayConfigBuilder` строит outbound-конфиг из `ServerEntity` (VLESS и
Shadowsocks — по официальной документации Xray-core, сверенной в этой
сессии; Trojan/VMess — по устоявшемуся, но не сверенному сегодня
паттерну). Экран «Серверы» — теперь стартовый: список серверов, кнопка
«Подключиться» реально проходит `VpnService.prepare()` (системный диалог
согласия) и стартует `SunflowerVpnService` с настоящим конфигом.

Не заработает по-прежнему: `LibXrayBridge` бросает исключение вместо
вызова .aar (не собран), а как именно TUN-режим сопоставляет трафик с
outbound в этой версии Xray-core — открытый вопрос, отдельный от самого
outbound-конфига (см. `ARCHITECTURE.md`, комментарий в
`XrayConfigBuilder`). То есть путь «нажал → дошло до Xray» теперь весь
настоящий, а вот «Xray принял конфиг и погнал трафик» — всё ещё нет.

## Статус: v0.3

Добавились: `SunflowerVpnService` (реальный VpnService.Builder, пишет
TUN fd в конфиг), WorkManager-воркер автообновления подписок (Hilt-
интегрированный), экран настроек (Kill Switch/Allow LAN/Auto connect —
реально в DataStore) и **экспериментальный** отдельный CI-джоб
(`build-libxray-aar.yml`), который пытается собрать `.aar` libXray
из исходников через Go+gomobile+NDK. Он изолирован от основной сборки
и запускается только вручную (workflow_dispatch), потому что часть его
шагов (версия NDK, ожидания build/main.py по env-переменным) не
подтверждена так же строго, как остальной проект — это единственное
место в репозитории с таким статусом, и это явно написано прямо в файле
джоба.

Даже после того, как этот джоб соберёт `.aar`, туннель не заработает
автоматически — нужно ещё (1) подключить сам файл в
`app/build.gradle.kts` и раскомментировать реальный вызов в
`LibXrayBridge`, и (2) построить экран «Серверы» с кнопкой
«Подключиться» и `VpnService.prepare()`, которого пока нет. Это
следующие два конкретных шага, а не «почти всё готово».

## Статус: v0.2 — Data + Parsing + Subscriptions реально работают

Экран «Подписки» — первая реально работающая фича целиком: URL → GET
(OkHttp, с опциональным `allowInsecure` только на этот запрос и HWID-cookie)
→ определение формата (Base64/plain/список ссылок) → парсинг VLESS/VMess/
Trojan/Shadowsocks → сохранение в Room с атомарной заменой серверов →
список с обновлением/удалением. Настройки (killSwitch/allowLan/
autoConnect/theme/device id) — в DataStore.

Tunnel-слой (`LibXrayBridge`/`TunnelEngine`/`TunnelManager`) реализует
настоящий протокол libXray (`Invoke(requestJSON)`, см. `ARCHITECTURE.md`),
но пока не может реально подключиться: сам `.aar` не собран — это
отдельная задача (Go + gomobile + Android NDK в CI), которую не стали
делать наспех вместе с остальным. `SunflowerVpnService` по той же причине
ещё не начат. Полная таблица статуса по слоям — в `ARCHITECTURE.md`.

## Сборка

Локальной сборки нет и не предполагается (весь workflow — с телефона,
без компьютера). Сборка идёт через `.github/workflows/build.yml`:

1. Залить содержимое этого архива в новый GitHub-репозиторий.
2. Push в `main` — Actions запустится автоматически. Либо запустить
   вручную через вкладку Actions → Android CI → Run workflow.
3. Готовый `sunflower-debug-apk` появится в Artifacts запуска.

`gradlew`/`gradle-wrapper.jar` в репозитории нет — CI ставит нужную
версию Gradle сам через `gradle/actions/setup-gradle`. Если когда-нибудь
понадобится собирать локально, `gradle wrapper --gradle-version 9.5.1`
сгенерирует обёртку.

## Release-сборка

CI собирал только debug. Теперь есть подписанный release-путь, но
намеренно НЕ автоматический — секретный ключ подписи не может появиться
сам по себе:

1. **Один раз**: Actions → "Generate Release Keystore (one-time)" → Run
   workflow. Скачать артефакт `sunflower-release-keystore` из этого
   запуска (доступен 1 день) — внутри `keystore-base64.txt` и
   `secrets-to-add.txt`.
2. Repo Settings → Secrets and variables → Actions → добавить 4 secrets
   по именам/значениям из этих файлов: `SUNFLOWER_KEYSTORE_BASE64`,
   `SUNFLOWER_KEYSTORE_PASSWORD`, `SUNFLOWER_KEY_ALIAS`,
   `SUNFLOWER_KEY_PASSWORD`.
3. Дальше при каждом релизе: Actions → "Android Release" → Run workflow.
   Готовый подписанный APK — в артефактах запуска.

Команда генерации keystore реально протестирована в песочнице перед тем,
как её класть в workflow (см. `generate-release-keystore.yml` —
там же зафиксирована находка: современный `keytool` по умолчанию создаёт
PKCS12-хранилище, где store- и key-пароль технически не могут отличаться).

Репозиторий стоит сделать приватным перед первым запуском — artifact с
ключом виден всем, у кого есть доступ читать Actions этого репо.

## Дизайн v0.8: таб-бар вместо кнопок навигации, «стеклянные» карточки

Нижний таб-бар (Серверы / Подписки / Настройки) заменил кнопки в
TopAppBar — три основных раздела теперь всегда на виду, как в iOS.
Карточки подписок/серверов — через переиспользуемый `GlassCard`
(полупрозрачный градиент + тонкая обводка + мягкая тень), кнопки со
скруглением-таблеткой, реальные иконки вместо текстовых кнопок и
юникод-звёздочек. Настоящего backdrop-блюра (то, что размывает контент
ЗА карточкой, а не саму карточку) сознательно нет — `Modifier.blur()` в
Compose блюрит сам элемент, не то, что за ним; для настоящего
glassmorphism нужны либо API 31+ RenderEffect-трюки, либо сторонняя
библиотека вроде Haze — ещё одна непроверенная версия-зависимость,
которую не стал добавлять без проверки. Сам промт (пункт 70) называет
градиент+обводку+тень допустимой заменой, когда полный blur слишком
дорог по производительности.
